# Architecture

> How Okapia is put together: the layers, the one image that carries two Macintosh, what exists exactly
> once, how memory is laid out, how time is kept, and where things live in the repository.

## Layers

```
            Basilisk II core                      SheepShaver core
  uae_cpu_2021 · ROM patches · ADB · disk    kpx_cpu · nanokernel ROM · the same
  SCSI · video · audio · ether · timer       ADB, disk, audio, extfs (symlinked)
                 │                                     │
   src/circle/ (68k platform layer)       src/circle/ + src/circle/sheepshaver/
   main · video · input · audio · tick    (the PowerPC platform layer)
                 │                                     │
                 └──────────────┬──────────────────────┘
                                ▼
     shared half: hal_circle (the board) · board_sound · mac_ram · rom_chime
                  okapia_boot (main) · src/firmware (boot menu)
                                ▼
                 circle-stdlib (newlib + libstdc++) → Circle
                                ▼
                           Raspberry Pi
```

Upstream shares its platform code between the two engines by **129 symbolic links** from
`SheepShaver/` into `BasiliskII/` (`adb.cpp`, `audio.cpp`, `disk.cpp`, `extfs.cpp`, `prefs.cpp`, `timer.cpp`,
`xpram.cpp`, `sys_unix.cpp`, `CrossPlatform/`, the whole `SDL/` directory). `src/circle/` takes the place of
`src/SDL/`, so most of it serves both engines by construction. The line between them falls on four points
only: `main`, `video`, `user_strings`, `sysdeps`.

Upstream Unix files reused unchanged: `Unix/extfs_unix.cpp` (shared folder) and `Unix/sys_unix.cpp` (disk
image access). `CrossPlatform/video_blit.cpp` supplies the pixel converters for both engines.

## One image, two Macintosh

`make -C src/kernel` builds both engines, partial-links each into one object (`engine-68k.o`,
`engine-ppc.o`), renames every symbol the PowerPC object *defines* with the prefix `ppc__` (the list,
`engine-ppc.rename`, is regenerated by `nm --defined-only` at each build), and links everything together.
Nothing in `external/` is touched.

- **The seam is two functions**, `OkapiaRun68k()` and `OkapiaRunPowerPC()` (`src/kernel/okapia_boot.h`),
  the only names left out of the rename. They have C linkage so a build rule can name them without knowing
  how the compiler mangles.
- **`okapia_boot.cpp` owns `main()`.** It enters the 68k engine first — its symbols keep their own names —
  and loops on what each engine returns: `OkapiaSwitchToPowerPC`, `OkapiaSwitchTo68k`, `OkapiaReboot`,
  `OkapiaHalt`.
- **Switching engines is a call, not a reboot.** The engine handed to does not open the boot menu again:
  `OkapiaRun*(bSwitched)` skips that one pass, because the shared firmware has just answered.
- **`--wrap` and the rename.** The linker looks for `__wrap_<name>` for the `<name>` it is given, so the
  prefix goes *inside* the `__wrap_`; and `__real_<name>` is never defined (the linker fabricates it), so it
  must be caught among the undefined symbols or the renamed hook calls the other engine's original.
- **`ld -r` kills `--wrap`.** A partial link resolves every reference inside its set, so wraps passed to the
  final link are silently ignored. They go on each engine's partial link (`ENGINE_WRAPS`).
  `objdump -d engine-68k.o | grep __wrap_` tells in a second whether a hook is alive.

## What exists once, and what exists twice

`SHARED_SRCS` in `src/kernel/Makefile` is compiled once into `obj-shared/`: the board (`hal_circle.cpp`),
its sound, chime and power-off (`board_sound_circle.cpp`), the Mac RAM block (`mac_ram_circle.cpp`), the
chime reader (`rom_chime.cpp`), the entry point, and the whole firmware. Everything else (`PLATFORM_SRCS`) is compiled once per engine, on purpose: it costs image size
and no correctness.

Two rules pull in opposite directions across that line:

- **A claim on the hardware belongs to the shared half.** A `static bool s_bArmed` in a per-engine file is two
  variables, and neither Macintosh sees the other's claim. Circle gives nothing back — an interrupt line
  connected twice asserts (`interrupt.cpp:145`), and a Circle assertion halts, which under QEMU looks like
  the emulator quitting on its own. The engine leaves its handler; the board holds the resource.
- **A symbol the PowerPC half references cannot be defined in the shared half.** The rename renames the
  reference with the definition; a definition in `obj-shared` keeps its bare name and the link fails.
  `ppc_check_ticks_quantum` is declared in a patched `ppc-cpu.hpp` and defined in
  `sheepshaver/cpu_ticks_circle.cpp`, both in the PowerPC half.

### Resources taken once for the life of the board

The Macintosh goes round more than once: a restart from Mac OS re-enters the start path, and the user can
switch engines. Before adding any registration, claim or `push_back` to a start path, ask what the fifth
restart does to it — and log the free heap per round; a number that does not move is the cheapest proof.

| Resource | Held by | Why it cannot be taken per start |
|---|---|---|
| Output frame buffer | `FwOutputClaim()` (`okapia_output.h`) | a claim per handover leaked 4.8 MB a round |
| Mouse | `okapia_input.cpp`, forwarded by `FwInputPassMouseTo()` | `CMouseDevice::RegisterStatusHandler` asserts on a second claim (`mouse.cpp:85`) |
| Microsecond timer and its IRQ | `BoardFineTick()` (`hal_circle.cpp`) | `ARM_IRQ_TIMER1` asserts when connected twice |
| Sound device | `BoardSoundClaim()` (`board_sound_circle.cpp`) | a sound device deleted while its DMA runs asserts or crashes |
| Mac RAM block | `MacRamClaim()` (`mac_ram_circle.cpp`) | a second 256 MB block is not there on a 1 GB board |
| Periodic timer slots | Circle keeps four, with no way to return one | the fifth start asserts |

`COkapiaBoard` is a singleton whose `Start*()` methods are idempotent. Circle's own objects that can fail
at construction (the USB host) are built with `new` after the logger exists, never as members: a member
constructor runs before the serial port and fails silently.

## Boot flow

1. **Board**: serial, logger, interrupts, timer and clock, console, card, log file on the card
   (`COkapiaBoard::Start`, `StartCard`).
2. **Preferences** from `/BasiliskII_Prefs`; time zone applied.
3. **Mac RAM block**, before any driver allocates (below).
4. **Startup chime** starts from a kernel timer ([Sound](../topics/sound.md#startup-chime)).
5. **USB**, and the firmware starts latching the keyboard at once (`FwInputWatch`): a key held from power-on
   reports only once.
6. **Firmware window**: two seconds of plain grey; Option, the `bootmenu` preference, or nothing bootable
   opens the boot menu ([Boot menu](../topics/boot-menu.md)).
7. **Engine**: the startup volume's System decides 68k or PowerPC; the other engine is entered by a call.
8. **Macintosh**: `InitAll()`, input, tick, then the interpreter until the Mac stops.
9. **Restart, switch or shut down** — see [Startup and shutdown](../topics/startup-and-shutdown.md).

## Memory

- **One block**, claimed at `ramsize + OKAPIA_MAC_BLOCK_OVERHEAD` (24 MB, `mac_ram_circle.h:29`) — sized
  for whichever engine needs more, so the second engine reuses it.
- **Claimed first.** Circle serves blocks larger than its largest bucket by walking forward through free
  space, so a quarter-gigabyte request made after USB or network stacks have allocated fails on a 1 GB board
  even though the memory is there. Only the card mount and the preferences (which give `ramsize`) come
  before it.
- **`HEAP_ANY`**: on a 4 GB Pi 4 the block lands above 1 GB (logged `Mac memory: 256 MB RAM at 0x40000040`).
- **68k layout** (`DIRECT_ADDRESSING`): Mac RAM at Mac address 0, ROM at `0x10000000`, host = Mac address +
  `MEMBaseDiff`. The Mac's frame buffer is allocated separately on the heap (16 MB).
- **PowerPC layout**: RAM at guest `0x10000000`, ROM right after it, then the interrupt stack, SheepMem and a
  16 MB frame buffer — see [PowerPC engine](../topics/engine-powerpc.md#memory-layout).
- **The heap is not executable**: `PXN=1` past `_etext`.
- **Kernel member constructors run before serial**, so any object whose construction can fail belongs after
  the log (the USB host, the console's two devices).

## Timing

**The Macintosh's 60 Hz is its unit of time**, not a display setting: every VBL increments `Ticks`, and the
Time Manager, cursor blink and application delays all rest on it.

- **The tick** is a hardware timer interrupt on core 0 that only sets flags. On Pi 3 and 4 it is a
  `CUserTimer` with a microsecond deadline, re-armed on an absolute schedule (`tick_circle.cpp`, through
  `BoardFineTick`). Circle's periodic handler fires at `HZ = 100` (`timer.h:30`), and 16,625 µs does not
  divide 10,000: a tick derived from it comes out 20, 10, 20 ms — right on average, and one frame in three
  half as long, which the Mac redraws its pointer on. The accumulator stays as the fallback for
  `RASPPI > 4`. Verified on the Pi 4: `Tick armed: system timer, microsecond deadline`.
- **A late tick is dropped, never repaid.** Circle re-arms its comparator by one period whatever the latency
  (`timer.cpp:577`); a catch-up of our own turned one delay into sixteen ticks at 0 ms and a 140 ms hole.
- **Anything that blocks belongs to the engine's own seam, never to the tick.** The tick runs at IRQ level,
  where waiting on the SD card is forbidden. The seams run between two guest instructions on the emulation
  thread:
  - 68k: `cpu_do_check_ticks()` (`cpu_ticks_circle.cpp`), fired when `emulated_ticks` wraps;
  - PowerPC: `powerpc_check_ticks()` (`sheepshaver/cpu_ticks_circle.cpp`), a seam kpx_cpu did not have,
    added by `patches/macemu/0004` because upstream always had a spare thread.
- **Both seams are paced by the clock, not by an instruction count.** The quantum is measured against the
  clock every 64 visits and corrected to hold 1 kHz (measured 999/s on the 68k, ~950/s on the PowerPC).
  An instruction count is a rate only on a machine whose speed never varies, and the input drain must be
  well faster than a mouse's ~100 reports per second. infinite-mac does the same for the same reason.
- The seams also carry, every five seconds, the clock watch, the performance report (`perfreport`) and the
  flush of the log to the card.

## Multicore

**Status: not implemented.** `ARM_ALLOW_MULTI_CORE` is commented out (`sysconfig.h:158`) and both engines
run on core 0 with the interrupts.

Circle's constraints (`doc/multicore.txt`): every peripheral IRQ is handled on core 0; the cooperative
scheduler runs on core 0 only; `ARM_ALLOW_MULTI_CORE` costs a little even single-core; most classes need a
`CSpinLock` to be used from another core.

The original plan, kept as the goal:

| Stage | Core 0 | Core 1 | Core 2 | Core 3 |
|---|---|---|---|---|
| S1 | IRQs, scheduler, I/O (SD, USB, network), tick | emulation loop | — | — |
| S2 | as S1 | as S1 | compositor | — |
| S3 | as S1 | as S1 | compositor | audio, disk |

What already respects it: the USB handlers only record (a ring for keys and buttons, an accumulator for
motion) and the emulation thread drains them ([Input](../topics/input.md)); anything that writes the card
runs in the engine seams. The [bottleneck study](../notes/research/bottlenecks.md) ranks the work.

## Repository layout

```
external/            submodules, pinned: circle-stdlib (Circle in libs/circle), macemu, hfsutils
patches/             macemu/*.patch and circle-stdlib/*.patch, applied by scripts/apply-patches.sh
reference/           study clones, fetched on demand, ignored by git
src/circle/          platform layer: 68k engine files and those shared by both engines
src/circle/sheepshaver/  PowerPC-only platform files (main, video, memory layout, seam)
src/circle/compat/   what newlib lacks: utime, ioctl, resolver stubs
src/firmware/        the boot menu, pure: no Circle type in it
src/firmware/circle/ the firmware's Circle side: window, USB bridge, output claim, specimen kernel
src/kernel/          the Okapia kernel: Makefile, both CKernel classes, okapia_boot
assets/              fonts (BDF), icons, strings.tsv — sources of generated tables
scripts/             build, run, test, card and generator scripts
tests/host/          host-side checks and renders
tests/smoke/         the Phase 1 Circle smoke kernel (C++ exceptions, frame buffer, SD)
tests/core-probe/, tests/link-probe/   compile and link probes of the Basilisk core
qemu/                development card contents (sd-contents/, ignored) and default preferences
docs/                this documentation
```
